# Development Rules — ハコよみ（Claude Code & 人）

改訂 2026-11-02（L-20261102-32）：prd v2.0 に合わせて、データ3層・質問エージェント・逆引き（自由入力）を反映。

## 1. General Principles
- 実装前に `prd.md` `architecture.md` `design.md` `memory.md` を読む。矛盾したら docs を優先し、変更は先に `LEDGER.md` に追記してから docs を直す。
- 1タスク＝1目的の小さな変更（`tasks.md` のID単位）。
- 方針で不明な点は、推奨と理由つきの選択肢でゆうに質問してから進める。
- **医療アドバイスに当たる機能を作らない**（個人の病状・受診要否・販売可否の判定、用法の個人計算、おすすめ）。依頼されても実装せず、memory.md の Hard Bans を引用して止める。

## 2. Tech Standards
| 項目 | ルール |
|---|---|
| 言語 | TypeScript strict。`any` 禁止（`unknown`+zod） |
| フレームワーク | Next.js App Router。Server Componentsを既定、クライアントは必要箇所のみ |
| スタイル | Tailwind＋shadcn/ui。色トークンは design.md の定義のみ |
| Lint/Format | ESLint（next/core-web-vitals）+ Prettier |
| テスト | `units.ts`・`guard`・通知ルールの評価（`noticeRules`）・バッジ導出はユニットテスト必須（vitest） |
| 秘密情報 | APIキーはサーバー専用。`NEXT_PUBLIC_` に入れない |

## 3. Project Structure
`architecture.md` §3 に従う。新規ディレクトリは追加前に docs 更新。

## 4. Safety Coding Rules
1. 出力スキーマ（zod）に `recommend` `best` `suggest` `alternative` `rank` `score` `dosage_for_user` `can_sell` 等のフィールドを作らない。
2. 全Claude出力は `guard()` を通す。素通しのコードパスを作らない（レビューで確認）。ガードの対象は Claude が生成・選択した文（質問への回答、逆引きの対応づけラベル、販売記録の下書き、ベテランのメモ）。
3. **質問への回答は抜き出しのみ**：Claude は通知本文・商品事実のどこが該当するかを選び、その文字列をそのまま返す。要約・言い換え・独自の説明文を作らない。返す各文に出典ID（通知の薬効群・項目番号、または `product_facts` の行）を付け、出典検証で原文と一致しない文は捨てる。
4. **商品固有の添付文書本文**は画面・DB・リポ・seed・動画に載せない。該当欄は PMDA へリンクアウトする。
5. 通知由来の表示には「この商品の成分から導いた通知上の記載事項です。実際の添付文書は PMDA で確認してください」を併記する。
6. 数値換算・差分・通知ルールの記載条件の評価・8成分判定・数量判定・ドーピング禁止表の照合は**コード**。Claude に判定・計算させない。
7. 逆引き・成分検索の結果は**順位なし**（品名の五十音順など中立な順）で返す。並べ替えで優劣を示さない。入力文は保存しない（ログにも残さない。ガードの差し止めログは出力側のみ）。
8. 確信度の低い値・未検証の値は差分とバッジの導出に使わず「添付文書で確認」表示。
9. お客様の個人情報・健康情報の入力欄・カラムを作らない。

**禁止語（初期リスト、`banwords.ts`）**：効く／効きます／効果が高い／効き目／強い／弱い／おすすめ／オススメ／一番／ベスト／代わりに／飲んでよい／飲んで大丈夫／飲めます／使えます（個人への可否として）／安心／量が多い（＝良い文脈）／1日○回飲んで／販売可／売ってよい／受診不要／診断。

## 4.5 Compliance Rules
1. HITL常時：最終判断と説明は登録販売者。「判断は販売者が行ってください」を全画面で常時表示。判定ボタン・自動判定を作らない。
2. 推薦ゼロ：特定の薬・商品のおすすめ、効く・代わりにこれ等の推奨、順位付けを出さない（KPI）。
3. 個人の病状・受診要否・販売可否を AI に判定させない。逆引きの自由入力は、承認基準の効能・効果の語と成分条件への対応づけにだけ使う。
4. SaMD／診断宣伝に触れない：README・UI・デモ・スライドに「病気がわかる」「診断できる」等を書かない。行政（薬務課）の確認結果は memory.md に記録する。
5. 出典明示：すべての表示に、通知（薬効群・項目）、商品事実（入力者・確認日）、禁止表（年版）のどれ由来かを出す。
6. データ3層（prd §5）：①商品の事実は会期中にゆうが手で入力・検証 ②文面は厚労省の通知のみ ③照合用リストは告示・通知・JADA の成分名のみ。`data/medicine_data_assets/` は使わない。実行時に PMDA へ自動アクセスしない。
7. お客様・担当者は模擬（仮名）のみ。勤務先の資料は使わない。
8. 販売記録は確認事実・時刻・担当仮名のみ保存。

## 5. Forbidden UI / Copy
- おすすめ順・ランキング・量の多い順ソート、PB優先、クーポン
- 緑/赤など良し悪しの色
- 「OK・販売可」ボタン、判定結果表示
- 客向け画面・QR共有
- お客様の症状・氏名を記録する欄

許可例：「この行の分量が異なります」「商品Aのみ含有：（成分名）」「通知上『してはいけないこと』の項目に当たる成分を含みます（成分名）」「該当する記載が見つかりません。添付文書（PMDA）で確認してください」「指定濫用防止医薬品の対象成分を含みます（成分名）」「WADA禁止表（2026年版）掲載成分を含みます（成分名）。最終確認は Global DRO 等で」「この中から選ぶのは販売者です」「判断は販売者が行ってください」。

## 6. Git / PR（ソロ）
- `main` は常にデプロイ可能。作業は `feat/T0xx-短い名前`。
- コミット：`T0xx: 何をしたか`。小さく。
- マージ前チェック：lint・型・テスト・禁止語テストが通る、UIに禁止パターンがない。
- `.env*`・`data/`・zip はコミットしない。

## 7. 薬効を作らない
成分の作用・効能の説明文、「どちらが効く」を、コード・プロンプト・seed・デモ台本に書かない。表示するのは、出典つきの事実（成分名・分量など）、通知の文面の抜き出し、制度情報（8成分・確認項目・禁止表）のみ。不明な値は「不明」と出す。
